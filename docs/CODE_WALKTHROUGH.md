# 코드 워크스루 — PiPER 마커 기반 Pick & Place

코드를 함께 보며 설명하기 위한 안내서. 리뷰 주제인 **제어 알고리즘 / 그리핑 /
마커 찾기** 세 가지를 2~4절에 나눠 담았다.

줄 번호는 작성 시점 기준이며, 코드가 바뀌면 `grep -n "함수명"`으로 다시 찾으면 된다.

## 1. 시스템 구성 — 먼저 볼 것

**진입점: [`src/piper_hw_pkg/launch/piper_real.launch.py`](../src/piper_hw_pkg/launch/piper_real.launch.py)**

이 런치가 띄우는 노드가 시스템 전부다. 인자 선언부(38~150행)를 먼저 보면
"무엇이 조정 가능한 값인가"가 한눈에 들어온다.

| 노드 | 파일 | 역할 |
|---|---|---|
| `piper_driver_node` | `src/piper_hw_pkg/piper_hw_pkg/piper_driver_node.py` | CAN으로 팔·그리퍼 구동, 60Hz 틱 발행 |
| `piper_gripper_node` | `src/piper_hw_pkg/piper_hw_pkg/piper_gripper_node.py` | 그리퍼 α-SMC 힘제어 |
| `piper_eih_camera_node` | `src/piper_hw_pkg/piper_hw_pkg/piper_eih_camera_node.py` | RealSense 손목캠 소스 + `link6→eih_cam` TF |
| `vision_node` | `src/vision_pkg/vision_pkg/vision_node.py` | ArUco 검출 → 마커의 로봇 좌표 |
| `arm_node` | `src/control_pkg/control_pkg/arm_node.py` | 픽앤플레이스 상태기계 |
| `piper_fake_amr_node` | `src/piper_hw_pkg/piper_hw_pkg/piper_fake_amr_node.py` | 시퀀스 개시 신호 + `body_link` TF |
| `robot_state_publisher` | (외부) | URDF → `link1~link6` TF |

### 데이터 흐름

```
관절각 ─→ robot_state_publisher ─→ body_link→link6 TF
                                        │
손목캠 영상 ─→ vision_node ←────────────┘
                   │  (ArUco + PnP + TF)
                   ↓
            마커의 body_link 좌표
                   ↓
              arm_node (상태기계)
                   │
         ┌─────────┴─────────┐
    목표점 스트리밍        열기/닫기
         ↓                    ↓
   piper_driver_node ←── piper_gripper_node
         │                    ↑
         └──── 개구부/토크 ───┘
```

**핵심**: 마커 위치 추정은 **팔의 순간 자세와 카메라 외부파라미터에 동시에 의존**한다.
손목에 달린 카메라라 팔이 움직이면 카메라도 움직이기 때문이다. 이 구조가 5절에서
설명할 캘리브레이션 문제의 배경이다.

### 시간 기준

드라이버가 60Hz 틱(`piper_driver_node.py:201` `_tick`)을 발행하고 상태기계와 그리퍼
제어가 여기에 동기화된다. 코드의 모든 시간 상수가 스텝 수로 표현돼 있다(900스텝 = 15초).

## 2. 제어 알고리즘

### 2.1 상태기계 — `arm_node.py:873` `_tick()`

phase 문자열 하나로 전이하는 단순 구조다. 각 phase 블록이 `elif ap == "..."` 으로
이어진다.

```
wait → hover → detect → pre → grasp → grip → lift → verify
                 ↑                                     │
                 └──────── 실패 시 재시도(최대 2회) ────┘
                                                       ↓ 성공
place_wait → place_ready → place_hover → place_detect → place_descend
           → place_release → place_retreat → place_home → place_done
```

| phase | 줄 | 하는 일 |
|---|---|---|
| `hover` | 898 | 파라미터로 받은 "물체 대략 위치"로 이동. **비전을 안 쓴다** |
| `detect` | 921 | 정지 상태로 첫 검출 → anchor 고정 |
| `pre` | 926 | 파지점 위 5cm까지 접근하며 실시간 추종 |
| `grasp` | 972 | 최종 하강. 도달 판정 후 grip으로 |
| `grip` | 1067 | 그리퍼 닫기 |
| `lift` | 1094 | 10cm 상승 |
| `verify` | 1105 | 파지 성공 판정 (3절) |
| `place_*` | 1130~ | 마커 기반 정밀 배치 (4.5절) |

**주의**: `place_lower`(1116)는 `use_marker_place=false`일 때만 도는 단순 경로다.
현재 기본값은 `true`라 `place_ready`(1130)부터가 주경로다.

### 2.2 목표점 스트리밍 — `arm_node.py:1301` `_move_l()`

목표를 한 번에 던지지 않고, **가상의 추종점을 매 틱 `v·Δt`만큼 목표 쪽으로 옮기며**
그 위치를 발행한다.

```python
step = speed * (MOVE_L_PERIOD/60.0)
self._move_l_pos = self._move_l_pos + remaining/dist*step
```

이렇게 하는 이유 둘:
- 구간별로 속도를 다르게 가져갈 수 있다 (2.3)
- 목표가 중간에 갱신돼도(재검출) 자연스럽게 따라간다

### 2.3 3단 감속 접근

| 구간 | 속도 | 목표 |
|---|---|---|
| hover | 0.10 m/s | 물체 윗면 위 138mm |
| pre | 0.05 m/s | 파지점 위 50mm |
| grasp | 0.025 m/s | 파지점 |

멀리서는 빠르게, 가까이서는 느리게. 느려야 근접 구간에서 마커 검출이 흔들리지 않는다.

### 2.4 두 가지 제어 모드 — `piper_driver_node.py:201` `_tick()`

| 모드 | phase | 명령 | 도달 확인 |
|---|---|---|---|
| **MOVE L** | `CARTESIAN_PHASES` (52행) | `EndPoseCtrl` | `ee_pose` 피드백으로 가능 |
| **MOVE J** | `JOINT_HOLD_PHASES` (47행) | `JointCtrl` | `/joint_states`로 가능 |
| 무명령 | 그 외 (`detect`, `verify`, `grip`) | — | 팔이 직전 목표 유지 |

### 2.5 ★ 명령 중복 제거 — 가장 오래 막혔던 문제

`piper_driver_node.py:222` 부근.

```python
if cmd != self._last_endpose:
    self._last_endpose = cmd
    self.piper.EndPoseCtrl(*cmd)
else:
    self._cmd_skipped += 1
```

**왜 필요한가**: 같은 목표를 60Hz로 재전송하면 펌웨어가 매 틱 MOVE L 궤적을 새로
시작한다. 가속 램프가 16ms마다 리셋되므로 저속 설정에서는 램프 구간만 반복하다
팔이 사실상 전진하지 못한다.

진단 근거 — 손목캠~마커 거리를 시간순으로 본 결과:

| 구간 | 경과 | 거리 변화 | 속도 |
|---|---|---|---|
| grasp (명령 스트리밍 중) | 28초 | 285.6 → 280.3 mm | **0.2 mm/s** |
| grip (명령 없음) | 8초 | 270.2 → 137.6 mm | **17 mm/s** |

명령이 끊기는 `grip` 단계에서 비로소 팔이 제대로 움직였다.

**함정**: 캐시는 단계가 바뀔 때 비워야 한다(`_on_arm_status`, 177행). 안 비웠더니
기동 시 `wait`의 `SEARCH_Q`가 남아 `place_home`의 같은 명령이 "중복"으로 걸러졌고,
로그는 복귀 완료를 찍었는데 팔은 제자리였다.

### 2.6 도달 판정 이중화

목표점 스트리밍이 끝난 것과 팔이 거기 도달한 것은 다르다.

- **카르테시안**: `arm_node.py:626` `_wait_physical_arrive()` — `ee_pose`와 목표의 거리
- **관절**: `arm_node.py:479` `_joint_settled()` — `/joint_states`와 목표 관절각 비교

z축은 3D 거리와 **별도로 더 좁게** 본다(1.5mm 대 4mm). XY는 몇 mm 어긋나도 손가락
사이에 들어오지만, z가 덜 내려가면 물체 윗모서리만 물게 되기 때문이다.

## 3. 그리핑

### 3.1 문제 설정

PiPER 그리퍼는 **힘을 직접 지령할 수 없다.** 개구부(위치)만 받는다. 그런데 물체를
적절한 힘으로 쥐려면 힘 피드백이 필요하다. 그래서 토크 피드백을 보며 지령 개구부를
조절하는 외루프를 건다.

제어 변수 α는 "닫힘 정도"이고 개구부로 선형 사상된다 (`piper_gripper_node.py:106`):

```
개구부 = (1 − α) × 60mm
```

### 3.2 슬라이딩 모드 제어칙 — `piper_gripper_node.py:132` `_smc_alpha_command()`

```python
s_surf = SMC_F_TARGET - F_contact          # 슬라이딩 면
sat = clip(s_surf / SMC_PHI, -1, 1)        # 경계층 포화 (채터링 방지)
da = clip(SMC_K_A * sat, -SMC_A_RATE, SMC_A_RATE)   # 변화율 제한
if self.holding and da < 0.0:
    da = 0.0                                # ★ holding 모드: 이완 방향 차단
α = clip(α + da, SMC_A_MIN, SMC_A_MAX)
```

**holding 모드의 이완 차단이 핵심이다.** 리프트 중에는 물체 무게와 관성으로 접촉력이
순간적으로 튀는데, 제어기가 이를 "너무 세게 쥐었다"로 오인해 풀어버리면 슬립이
심해진다. 조이는 방향은 계속 허용하므로 미끄러지면 더 잡는다.

### 3.3 토크는 어디서 오는가

**전류가 아니라 펌웨어가 계산해 CAN으로 보내주는 값을 그대로 읽는다.**

```
그리퍼 펌웨어 ─(CAN 0x2A8, Byte 4-5, int16, 단위 0.001 N·m)─→ piper_sdk
  → piper_driver_node.py:276  gs.grippers_effort / 1000.0
  → /piper/gripper_feedback
  → piper_gripper_node.py:95  abs()  → SMC의 F_contact
```

- 별도 토크센서는 없다
- 팔 관절은 전류(`current`)를 따로 주는데 **그리퍼만 토크로 환산해서 준다**
- 환산 방법은 벤더가 공개하지 않았다 → **절대 파지력과의 대응은 모른다**

**★ 부호 함정**: 닫는 방향 저항은 **음수**로 들어온다(여는 쪽이 양수). 이를 모르고
`F_con >= 0.3`을 비교하면 항상 실패해서, 세게 잡고 있는데도 "접촉 미감지"로 뜨고
SMC가 계속 더 닫으라고만 명령해 펌웨어 토크 한계까지 밀어붙인다.

### 3.4 접촉 판정과 정착 — `piper_gripper_node.py:141` `_tick()`

1. 워밍업 2틱은 판정 제외
2. 토크가 임계값 이상인 프레임이 **연속 5회** 쌓이면 접촉 확정
3. 접촉 후 20틱 경과 + `|F_target − F_contact| < Φ` 이면 정착 완료

실측(16.36mm 큐브): 접촉 감지 41틱 / 피크 1.61 N·m / 정착 1.51 N·m (목표 1.5).

### 3.5 파지 성공 판정 — `arm_node.py:644` `_verify_by_gripper()`

**접촉력만으로는 판정할 수 없다.** 빈손이어도 손가락끼리 맞닿으면 저항이 생겨
접촉으로 잡힌다. 두 상황을 가르는 것은 **개구부**다.

- 물체를 물었으면 손가락이 물체 폭에서 멈춘다
- 헛집으면 손가락이 서로 닿을 때까지 닫힌다

| 조건 | 판정 |
|---|---|
| 최소 개구부 < 하한 | 헛집음 또는 놓침 |
| 그립 직후 대비 3mm 이상 추가 폐쇄 | 리프트 중 슬립 |
| 개구부 > 상한 | 물체를 안 물었거나 덜 닫힘 |
| 접촉 플래그 없음 | 실패 |

리프트 전 구간의 **최소값**을 보는 것이 중요하다. 마지막 값만 보면 중간에 놓쳤다가
다시 벌어진 프레임에 속는다.

**★ 개구부 보고값의 상수 오프셋**: 16.36mm 물체를 정상 파지했는데 **25.9mm로 보고**된다.
패드 두께 + 영점 미설정 때문이다. 물체 폭만으로 임계값을 잡으면 상한을 0.5mm 차이로
통과하므로, `grip_stroke_offset_mm`(기본 9.5)로 판정선을 보고값 스케일로 옮긴다.

## 4. 마커 찾기

### 4.1 검출 파이프라인 — `vision_node.py:426` `_on_eih_image()`

```
640×480 컬러 (카메라 노드가 왜곡보정 후 발행)
  ↓ ArUco 검출 (서브픽셀 코너 정밀화)
  ↓ solvePnP IPPE_SQUARE — 평면 마커 전용 해법
  ↓ 두 해 중 법선이 카메라를 향하는 쪽 선택
  ↓ 재투영 게이트
  ↓ 축 부호 변환 + TF(body_link←eih_cam)
마커의 body_link 좌표 + yaw
```

### 4.2 평면 마커의 자세 이중해 — `vision_node.py:358` `_solve_top_facing()`

정사각형 평면 마커는 원리적으로 **두 개의 자세 해**를 갖는다. 마커 평면을 대칭면으로
뒤집은 자세가 거의 같은 영상을 만들기 때문이다.

```python
for kk, (rv, tv) in enumerate(zip(rvecs, tvecs)):
    R, _ = cv2.Rodrigues(rv)
    if R[2, 2] > best_tz:       # 법선이 카메라를 향하는 해
        best_tz = R[2, 2]; best = tv
```

### 4.3 재투영 오차 — `vision_node.py:387` `_eih_reproj_ok()`

**rqt 디버그 창의 `rep=8.29px`가 이 값이다.** 추정한 자세로 마커 네 코너를 다시
영상에 투영했을 때, 실제 검출된 코너에서 몇 픽셀 어긋나는지의 RMS다.

**★ 절대 px 값으로 거르면 안 된다.** rep은 스케일 불변이 아니다.

| 손목캠~마커 | rep | 마커 한 변 대비 |
|---|---|---|
| 280 mm | 0.05~0.35 px | 0.1~0.7 % |
| 137 mm | 6.0 px | 7.4 % |
| 121 mm | 8.3 px | 9.1 % |

차체캠 경로의 3px 기준을 손목캠에 그대로 적용하면 **정밀도가 가장 필요한 파지 직전
구간이 통째로 기각된다.** 그래서 마커 한 변의 픽셀 길이로 나눈 상대 오차를 주 게이트로
쓴다. 현재 기본값(상대 20% / 절대 30px)은 거의 거르지 않는 관측용 수치다 — `detect`
단계에는 타임아웃이 없어서, 근거 없이 조인 값이 모든 프레임을 기각하면 시퀀스가
그 자리에서 멈추기 때문이다.

### 4.4 손목캠 외부파라미터 캘리브레이션 — `eih_cam_calib.py`

가장 오래 막혔던 문제이고 방법론이 볼 만하다.

**문제**: `link6→eih_cam` 변환에 초기에는 **병진 3개만** 주었다. 카메라가 팔 축과
나란하다고 본 것이다. 실제로는 기울여 장착돼 있었다.

**왜 병진만으로는 안 되는가**:

```
병진 오차 → 거리와 무관하게 일정
각도 오차 → 거리에 비례   (Δp ≈ d · Δθ)
```

그래서 특정 거리에서 맞춰도 거리가 바뀌면 다시 틀어진다. 더 심각한 건 동적 영향이다.
팔이 다가갈수록 추정 마커 위치가 움직이고, 실시간 재검출이 그 움직임을 따라가면서
목표점이 끌려다니다 결국 헛집는 연쇄가 반복됐다.

**해법 — 불변성 기반 자기정합 추정**: 마커의 참값 위치를 모르는 채로 풀 수 있는
조건을 썼다. 마커를 고정하고 팔 자세만 바꾸면, 외부파라미터가 정확할 때 마커의
body 좌표는 자세와 무관하게 같아야 한다. 따라서 **자세 간 분산을 최소화**하면 된다.

```
q_i = R_i ( R_cam(θ_p, θ_r) · s · p_i + o ) + t_i

min Σ ‖q_i − q̄‖²        (q̄ = 자세 평균)
```

목적함수에 마커의 참값이 없다는 것이 핵심이다. 자기정합성만으로 해가 결정된다.

**중첩 모델 비교로 원인 분리** (`eih_cam_calib.py:_report`):

| 모델 | 자유 파라미터 | 편차 RMS |
|---|---|---|
| 현재 설정 | 없음 | 10.4 mm |
| **회전만** | pitch, roll | **3.8 mm** |
| 회전 + 병진 | + x, y, z | 개선 없음 |
| 회전 + 병진 + 스케일 | + s | 개선 없음 |

회전만 푸는 단계에서 편차가 급감했으므로 원인은 회전, 그중 pitch였다.
추정값 **27.5°** — 각도계로 쟀던 40.0°가 **12.5° 틀렸다.**

**퇴화해 방어**: 스케일을 제약 없이 열면 `s → 0`이라는 가짜 해가 있다. 모든 관측이
손목 회전중심 한 점으로 모이면 분산이 0이 되기 때문이다. 경계(`s ∈ [0.5, 2.0]`)와
"관측 거리 변화가 150mm 미만이면 경고"로 막는다.

### 4.5 Place — 시야가 가려지는 문제

Pick에서는 그리퍼가 비어 있어 마커를 끝까지 볼 수 있지만, place에서는 **쥔 물체가
시야를 가린다.** 마커 위에 그대로 올리면 마커가 덮여 재검출도 끊긴다.

**대응 셋** (`arm_node.py:562` `_place_point_marker_inset()`):

1. **마커에서 비켜 놓는다** — 마커 중심에서 마커 한 변(35mm)만큼 이동. 방향은
   `place_inset_mode`로 고르며 기본은 **마커 자신의 −Y**. 마커를 비스듬히 붙여도
   기준이 따라 돈다. 마커 방향은 vision이 yaw로 함께 발행한다(`_marker_body_yaw`, 377행).
2. **릴리즈 높이를 물체 바닥 기준으로 계산**
   ```
   손끝 z = 마커 z + 릴리즈갭 + (물체높이 − 파지깊이)
   ```
   손끝은 물체 윗면보다 `grasp_depth_extra`만큼 아래를 쥐고 있으므로,
   손끝~물체 바닥 거리가 `물체높이 − 파지깊이`다.
3. **맹목 하강** — 최초 검출점을 고정하고 하강 중에는 갱신하지 않는다. 부분 오클루전
   상태의 PnP는 코너 일부만 보고 엉뚱한 자세를 낸다.

검증: 마커를 물리적으로 58° 돌렸더니(yaw 103.1° → 161.3°) 오프셋 방향이 그대로
따라갔고, 같은 런에서 베이스 방향(`radial`)과는 62.7° 갈렸다.

### 4.6 파지점 유도 — `arm_node.py:529` `_grasp_point()`

마커는 물체 중심이 아니라 **윗면**에 있으므로 두 번 보정한다.

```
손끝  = 마커 − 파지깊이 · ẑ            (수직 방향)
명령점 = 손끝 − 그리퍼길이 · â          (접근축 방향)
```

**★ 두 보정을 합쳐서 한 번에 빼면 안 된다.** 접근 각도가 0이 아닐 때 내려간 만큼
옆으로도 밀린다. 현재 pick은 수직접근(0°)이라 둘이 같지만, place는 pitch를 바꿀 수
있게 되어 있어 분리가 필수다.

접근 pitch가 0°면 z성분만 남아 다음으로 단순해진다:

```
z_명령 = 마커z + ee_grip_offset − grasp_depth_extra
```

실측 검증: 마커 z = −102.1mm일 때 −102.1 + 121 − 8 = **+11.0mm**, 실제 산출 +11.9mm.

### 4.7 실시간 추종과 오검출 기각 — `arm_node.py:854` `_eih_accept()`

`pre`와 `grasp` 구간에서 매 프레임 재검출해 파지점을 갱신한다. 다만 오검출이
통과하면 위험하므로 **최초 검출(anchor) 대비**로 제한한다.

직전값 대비가 아닌 이유: 초기 구현이 그랬는데 **2mm짜리 보정이 787번 누적돼 150mm까지
표류**했다.

한계는 **축별로 다르다.** 결과의 심각도가 다르기 때문이다.

| 축 | 오검출이 통과하면 | 한계 |
|---|---|---|
| XY | 헛집음. 재시도로 복구 | 관대 (pre 120mm / grasp 150mm) |
| **z 아래** | **손가락이 테이블을 찍음** | 20mm clamp, 50mm 초과는 기각 |

### 차체 카메라 코드는 왜 남겼나

`vision_node.py:244` `_on_chassis_image()`와 `arm_node.py:595`
`_verify_by_chassis_cam()`은 현재 실행되지 않는다. 차체 카메라가 없어

판정과 교차검증할 수 있다. 파라미터 하나로 되살아나도록 코드 경로를 보존한 것이다.

## 6. 예상 질문 대비

### "정밀도 0.9mm는 무슨 뜻인가"

**명령한 목표점과 펌웨어가 보고한 실제 위치의 거리**다. 즉 제어 추종 오차다.

여기에 들어가지 **않은** 것: 비전의 마커 위치 추정 오차, 카메라 외부파라미터 잔차,
`ee_grip_offset` 보정 오차, 펌웨어 FK 자체 오차, 기구 처짐.

**"그리퍼가 물체 실제 중심에서 0.9mm 안에 있다"는 뜻이 아니다.** 그걸 말하려면
물체 참값 위치를 아는 외부 계측이 필요한데 없다.

정당하게 주장할 수 있는 것 셋:
1. 제어 추종 오차 0.9mm — 명령점에 정확히 도달했다
2. 캘리브레이션 잔차 3.8mm RMS — 절대 정확도에 가장 가까운 지표
3. 16.36mm 물체를 8mm 깊이로 반복 파지 성공 — 전체 오차가 성공 범위 안이라는 간접 증거

### "SMC 목표 토크 1.5 N·m는 어떻게 정했나"

**실측으로 튜닝한 값이 아니다.** 코드에 `TODO(실측 필요)`로 표시돼 있다.
현재 타겟에서 목표에 수렴하고 놓치지도 않는 것은 확인했으나, 물체 재질이나 무게가
바뀌면 재튜닝이 필요하다. 펌웨어의 토크 산출 방법이 비공개라 절대 파지력과의
대응도 모른다 — 정확한 파지력이 필요하면 로드셀로 대조해야 한다.

### "움직이는 물체도 잡을 수 있나"

설계상 `pre`/`grasp`에서 추종하지만 **실기 미검증**이다. 그리고 물체가 움직이는
동안에는 도달 판정(3D 4mm 및 z 1.5mm)을 만족하지 못해 **그리퍼가 닫히지 않는다.**
"따라간 뒤, 멈추면 잡기"가 정확한 표현이다.

한계 셋: 최종 하강 속도 25mm/s, 파지 직전 화각 여유 85mm, 근접 구간 검출률이
런마다 100%↔67%로 흔들린다.
